  Below is a practical, non‑code design you can hand straight to the devs.

  A. “Element Picker” flow (dev‑tools style)

  Goal: let users point‑and‑click the three parts the bridge needs—input, send, history—so the extension doesn’t hard‑code fragile selectors.

  Enter Learn Mode

  User clicks “Pick elements” (extension popup).

  Content script injects a lightweight overlay (Shadow DOM) and temporarily disables pointer‑events on it so hovers reach underlying elements.

  Hover & highlight

  On mousemove, we draw a highlight box around the element under the cursor (like Chrome DevTools).

  Tooltip shows role/name (e.g., [role="textbox"] “Type a message”), tag, and a candidate selector score.

  Click to capture (three times)

  Input box → capture.

  Send button → capture.

  Chat history (scroll container) → capture.

  Generate a robust “selector set” for each capture

  Store multiple fallbacks:

  ARIA/role selector (e.g., [role="textbox"] + accessible name).

  CSS path pruned to stable anchors (ids/labels/data‑attributes), no brittle nth‑child chains.

  Text/label proximity (e.g., button with aria-label~="Send" near the textbox).

  Persist a domain profile { origin, selectors: { input: […], send: […], history: […] } } in chrome.storage keyed by site.

  Validate immediately

  Resolve selectors in priority order and simulate a dry run: focus input, insert test text via proper events, click “send” in preview mode (no real post), and watch for a 
  MutationObserver on the history container.

  Show green checks or ask the user to re‑pick if a selector fails.

  Save profile & run

  “Start chatting” arms the bridge with user‑approved selectors.

  If a selector later fails (layout change), show “Selectors broke—Re‑learn?” and bounce back to Learn Mode.

  Why this works: The user—not us—chooses the elements as rendered today; we record multiple resilient anchors and re‑validate at runtime. This is the most robust way to support many 
  chat UIs without per‑site code.

  B. Teams‑specific realities (and how we handle them)

  ContentEditable input: Teams uses a rich contenteditable composer. Don’t set .innerText. Instead: focus, set a Range, insert via execCommand('insertText', …) or InputEvent with 
  beforeinput → input to trigger React’s state.

  Virtualized history: Large threads render only visible messages. Our MutationObserver watches for appended message nodes in the chosen container and extracts only visible text (no 
  hidden APIs).

  Dynamic classes & testids: Prefer ARIA roles/names and label proximity. Treat data-testid as a hint, never the sole selector. Re‑score anchors each load.

  Iframes/PWA windows: Enable all_frames: true and scope to the active tab. If a message pane lives in a cross‑origin iframe, fall back to manual copy‑paste (we do not bypass origin 
  policies).

  Anti‑bot / rate gates: Never synthesize human behavior beyond basic focus/type/click; no CAPTCHA workarounds. If Teams signals blocking/rate limiting, stop and surface to the user.

  Bottom line: It will work—and it’s the right UX for a general chat bridge—but it’s inherently fragile compared to the Teams Bot/Graph connector. So we ship both: API first;
